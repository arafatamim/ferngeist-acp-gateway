# Contract Changelog

This is the **contract** changelog: it records changes to the gateway↔client
**protocol contract** (HTTP API shapes and semantics, ACP WebSocket frames, push
payloads, and the advertised `protocolVersion`) and the versioning policy that
governs them.

For the **full release changelog** (what shipped in each version, generated
from conventional commits), see `CHANGELOG.md` (generated by git-cliff; run
`task changelog`). This file is intentionally narrower: it is the record a
client maintainer reads to know whether a gateway update changes what the app
must do.

All changes to the gateway↔client **contract** (the HTTP API surface, the ACP
WebSocket frame shapes, push payloads, and the advertised `protocolVersion`)
are recorded here. Semantic changes — a field's meaning or the behavior a client
relies on — are listed even when the JSON shape is unchanged, because those are
exactly the changes that silently break a client.

Format:

- `[breaking]` — an older client will misbehave against the new gateway; a
  `protocolVersion` bump is required and the client gate will refuse.
- `[additive]` — a new endpoint, field, or optional behavior. Older clients
  ignore it; no bump required.
- `[semantic]` — a field's meaning changed but the JSON shape did not. A bump
  is required; the client gate will refuse.

Entries end with the date and the short hash of the commit that introduced
the change, linked to the commit on GitHub, so any claim can be checked
against the code.

## Versioning policy

- `protocolVersion` (served in `GET /v1/status` and the mDNS
  `protocol_version` TXT record; single constant in `internal/api/server.go`)
  is bumped only on `[breaking]` or `[semantic]` changes.
- `[additive]` changes never bump the version — an old client still works, and
  the client gate would otherwise force a needless update.
- When a bump is required, add the entry *and* bump the constant in the same
  change, so a release always ships a coherent version + changelog.
- Every contract-visible change gets a changelog entry with a date, even if it
  does not bump the version.

## Release tags

The **build** version (the daemon binary's `--version` and the mDNS
`gateway_version` TXT record) is separate from the **contract** version above.
Releases are tagged with semver (`v0.6.0` … `v1.2.0` so far); the Taskfile
derives the build version from `git describe`. They are independent and should
not be coupled. Full release notes live in GitHub Releases.

## History

- Unreleased:
- `[semantic]` `GET /v1/runtimes/{id}/git/status` returns `changed: []`
  for a clean tree, correcting the previous `null` response. Compare mode
  also returns an empty array when no files differ. No protocol version bump:
  this restores the documented array contract.
  (2026-10-25)
- `[semantic]` `POST /v1/agents/{agentId}/stop` stops the agent only for the
  calling device: it closes the sessions that device holds for the agent and
  leaves other paired devices' sessions and agent processes running. It returns
  `404` when the calling device has no live session for the agent. Shipped
  without a `protocolVersion` bump: a single-device client sees identical
  behavior, so the gate would force a needless update. (2026-10-23)
- `[additive]` Push payloads carry an optional `branch` — the branch of the
  managed worktree the chat runs in — so a client can show "feat-x finished"
  without a `/v1/worktrees` round trip. Absent for chats outside a worktree.
  (2026-10-22)
- `[additive]` `POST /v1/worktrees` accepts remote branches (e.g.
  `origin/feat-x`) and PR numbers (`pr/123`, `pull/123`, `origin/pr/123`) as
  the `base`, fetching the ref on-demand before checkout and validating refs
  strictly. (2026-10-21)
- `[additive]` `GET /v1/worktrees` lists every git worktree of the
  repositories the gateway knows, including ones made outside it (plain git,
  editors, other agent tools), and takes an optional `?repo=<absolute path>`
  to list one repository. Those worktrees carry a folder-derived `id` and
  accept every `/v1/worktrees/{worktreeId}` operation. (2026-10-22)
- `[additive]` `GET /v1/worktrees/{worktreeId}` — one worktree in the list's
  shape (`ahead`, `behind`, `dirty`, `chats`). (2026-10-21)
- `[additive]` `GET /v1/worktrees` (and the rebase response) gain `chats`: the
  ACP session ids of the running chats working in each worktree. Omitted when
  none runs. (2026-10-21)
- `[additive]` `GET /v1/worktrees/refs?repo=<absolute path>` — the
  `/git/refs` payload (`default` and `refs`) for a repository named by path, so a
  client can offer a base branch before any chat exists in it. Needs `control`
  scope, like `POST /v1/worktrees`. (2026-10-21)
- `[additive]` `POST /v1/worktrees/{worktreeId}/rebase` — rebases the worktree's
  branch onto its base ref and responds with the worktree as `GET
  /v1/worktrees` lists it. A conflicted rebase is aborted and the branch is
  left as it was. (2026-10-20)
- `[additive]` `POST /v1/worktrees/{worktreeId}/merge` — lands the worktree's
  branch on its base branch in the main checkout (a fast-forward, or one squash
  commit with `squash` and `message`), optionally deleting the worktree and its
  branch once merged; response `{"commit", "worktreeDeleted",
  "branchDeleted"}`. (2026-10-20)
- `[additive]` `POST /v1/worktrees/{worktreeId}/push` — pushes the branch to
  `origin` (setting its upstream, never force-pushing) and, with `pr: true`,
  opens a pull request through the `gh` CLI; response `{"pushed", "prUrl"}`.
  (2026-10-20)
- `[additive]` `POST /v1/paths/missing` — reports which of the given absolute
  paths no longer exist on disk, so a client can mark chats whose working
  directory (typically a removed worktree) is gone. Nothing is stored.
  (2026-10-22)
- `[additive]` `GET /v1/worktrees` entries gain `behind` — commits the base ref
  gained since the fork, so a stale worktree is easy to spot — omitted when the
  worktree has no base ref or it no longer resolves. (2026-10-20)
- `[additive]` `GET /v1/worktrees` entries gain `merged`: all of the branch's
  own commits are on its base ref, whether they landed by fast-forward, merge,
  rebase or squash, so a client can suggest cleanup. Omitted when the base ref
  no longer resolves. (2026-10-22)
- `[additive]` `GET /v1/worktrees` counts `ahead` from the merge-base of the
  branch and its base ref instead of the fixed `baseCommit`, so a rebased
  worktree no longer counts the upstream commits the rebase picked up — the
  same rule the managed-worktree `git/diff` endpoint uses. Not `[semantic]`:
  the field still means the commits the branch adds over its base, and only a
  worktree whose base moved reports a different number, so no `protocolVersion`
  bump. (2026-10-20)

- `v1.2.0` — branch comparison, workspace file listing, clock-skew recovery and
  direct bun/node npm launches; additive only, `protocolVersion` stays `v2`:
- `[additive]` `GET /v1/runtimes/{id}/git/diff` (whole-tree, no `?path=`) —
  the body is gzipped when the client sends `Accept-Encoding: gzip`, like
  `/files/list`; the JSON is unchanged. No `protocolVersion` bump: clients
  that do not ask for gzip get the plain body (2026-10-19,
  [cba44fe](https://github.com/arafatamim/ferngeist-acp-gateway/commit/cba44fe))

- `[additive]` `GET /v1/runtimes/{id}/git/log` reports `baseCommit` outside a
  managed worktree too. For any other checkout it names the commit the
  checked-out branch started from — the oldest `branch: Created from …` reflog
  entry — falling back to the merge-base with `origin/HEAD`, `main` or `master`
  when the reflog no longer records the creation. It is omitted (`HEAD`) for a
  detached HEAD, the trunk itself, and a branch whose own commits the trunk
  already contains, and it keeps its existing meaning inside a managed worktree
  (the worktree's merge-base with its recorded base ref). A client that reads
  the field now gets the marking on plain checkouts too; one that does not is
  unaffected. No `protocolVersion` bump. (2026-10-19,
  [1628f12](https://github.com/arafatamim/ferngeist-acp-gateway/commit/1628f12))

- `[additive]` Clock-skew recovery for proof-of-possession. `GET /v1/status`
  gains `serverTime` (the gateway's clock, RFC 3339 UTC). Every auth rejection
  (the `401`s and scope `403`s from the credential gate) gains a stable `code`
  (`proof_required`, `proof_invalid`, `proof_expired`, `proof_replayed`,
  `credential_missing`, `credential_invalid`, `credential_expired`,
  `credential_grace_expired`, `credential_scope`,
  `legacy_credentials_disabled`) and `serverTime`. On `proof_expired`, a client
  should set its proof clock offset to `serverTime - localNow`, re-sign with a
  fresh nonce, and retry once. Clients should classify rejections by `code`
  rather than by the text. The `proof_expired` message now reports the skew,
  but it still contains `proof expired`, so clients that match on that text
  keep working. No `protocolVersion` bump: older clients ignore the new fields.
  (2026-10-19, [3adc537](https://github.com/arafatamim/ferngeist-acp-gateway/commit/3adc537))

- `[additive]` `GET /v1/runtimes/{id}/files/list` — lists the tracked and
  untracked, non-ignored files under the session's project directory (the
  same root `/files?path=` reads): `{ "files": [...], "truncated": false }`,
  repository-relative and sorted, deduplicated, capped at 50,000 paths, and
  gzipped when the client sends `Accept-Encoding: gzip`. Read scope required;
  `404` for an unknown `acpSessionId`, `422` for a non-repo cwd or missing
  git; no ACP schema equivalent (gateway-defined). No `protocolVersion` bump:
  a gateway without it answers `404` with no envelope, which the client reads
  as "unsupported" (2026-10-19, [537e833](https://github.com/arafatamim/ferngeist-acp-gateway/commit/537e833))

- `[additive]` `GET /v1/runtimes/{id}/git/log` — each page gains `total`: the
  size of the walk the page comes from (`git rev-list --count <head>`, or
  `--not <ref>` in compare mode), so a client can size its history list from
  any page. It ignores `skip`, `limit` and `beyond`, is `0` for an empty
  repository or an empty range, and leaves `hasMore` authoritative for paging.
  Always present; a gateway that predates the field omits it, which is how a
  client tells that apart from a real `0`. A count failure fails the request
  with the walk's `422` rather than dropping the field. No `protocolVersion`
  bump: an older client ignores an unknown field. (2026-10-18, [ac63075](https://github.com/arafatamim/ferngeist-acp-gateway/commit/ac63075))

- `[additive]` Branch comparison for the git sheet:
  `GET /v1/runtimes/{id}/git/refs` lists local branches, `origin/*` refs and
  tags (each with `kind`, `isHead`, and a `default` hint), and `compare=<ref>`
  points `/git/status`, `/git/diff` and `/git/log` at another ref's tip
  instead of `HEAD` (or a managed worktree's base): a two-dot, tip-to-tip
  comparison with uncommitted work included. `/git/status` returns the strict
  `git diff <ref>` file set (flat, no staged/unstaged grouping) and echoes
  `compare` plus the resolved `compareCommit` only when an explicit
  `?compare=` was honoured — a worktree's merge-base sha is never reported as a
  comparison. A gateway without `/git/refs` answers `404`, which the client
  uses to hide the whole affordance. (2026-10-18, [f81472e](https://github.com/arafatamim/ferngeist-acp-gateway/commit/f81472e))

- `[additive]` `GET /v1/runtimes/{id}/git/status` changed-file objects gain
  `staged`: `true` when the index holds a change (the `X` of the porcelain `XY`
  pair), `false` for worktree-only edits, untracked files, and unmerged
  (conflicted) entries. `added`/`removed` are unchanged — they still count the
  whole `HEAD` → working-tree delta — so a partially staged file reports
  `staged: true` with both halves counted together. Also present (always
  `false`) on the `/git/commits/{sha}` file shape, whose files are the commit's
  own changes. (2026-10-16, [377e74e](https://github.com/arafatamim/ferngeist-acp-gateway/commit/377e74e))

- `v1.1.0` — commit history, detached turn results and rebase-safe worktree
  diffs; additive only, `protocolVersion` stays `v2`:
- `[additive]` Commit history endpoints: `GET /v1/runtimes/{id}/git/log`
  (paged commit list pinned by `head`, with refs, `pushed`, `remoteUrl` and,
  in a managed worktree, `baseCommit`) and `GET /v1/runtimes/{id}/git/commits/{sha}`
  (files changed vs the first parent). `GET /v1/runtimes/{id}/git/diff` accepts
  `commit` and `oldPath` to diff one file of a commit; without `commit` it is
  unchanged. Changed-file objects gain optional `oldPath`, set only by
  `/git/commits/{sha}`. (2026-10-14, [5548fe5](https://github.com/arafatamim/ferngeist-acp-gateway/commit/5548fe5))
- `[additive]` `_ferngeist/resumed` gains an optional `"truncated": true`
  param: the per-session replay buffer (8 MiB) evicted its oldest frames, so a
  gateway-restored session starts mid-conversation with earlier history
  missing. Omitted when the history is intact. (2026-10-13, [b07ff96](https://github.com/arafatamim/ferngeist-acp-gateway/commit/b07ff96))
- `[additive]` `_ferngeist/turn_result` — a new gateway→client notification on
  the ACP WebSocket, sent when a `session/prompt` finished while no client was
  attached: `{"jsonrpc":"2.0","method":"_ferngeist/turn_result","params":{"sessionId":…,"stopReason":…,"usage":…,"durationMs":…}}`.
  The detached reply is dropped with nothing left to route, so the pump keeps
  the turn's outcome per ACP session (latest wins; a new prompt clears it) and
  replays it ahead of the next connection's `session/load` or `session/resume`
  reply — before the SDK resolves that call — so the app learns the stop
  reason, the token usage and the turn length instead of leaving the context
  meter stale and the turn untimed. Clients that ignore unknown methods are
  unaffected. `session/resume` now restores like `session/load`: it records
  its session for redelivery, so unanswered agent requests are re-sent after a
  resume too. (2026-10-13, [eb4dfb8](https://github.com/arafatamim/ferngeist-acp-gateway/commit/eb4dfb8))
- `[additive]` `session/prompt` results gain `_meta.ferngeist.durationMs`: how
  long the turn ran, in milliseconds, from the prompt reaching the gateway to
  the agent's reply, measured on the gateway's monotonic clock. A client whose
  connection stalled (a dozing phone) hears the reply late, so it should time
  the turn with this instead of its own clock. Any `_meta` the agent sent is
  kept. Only on the result sent to the connection that issued the prompt;
  error replies and `_ferngeist/turn_ended` do not carry it. (2026-10-13, [b3dd51b](https://github.com/arafatamim/ferngeist-acp-gateway/commit/b3dd51b))
- `[additive]` Managed-worktree git endpoints (`GET /v1/runtimes/{id}/git/status`
  and `/git/diff`) — the base they compare against is now `git merge-base` of
  the branch the worktree was cut from and the worktree's `HEAD`, instead of
  the fixed `baseCommit` recorded at creation. After the worktree's branch is
  rebased onto a newer base, the diff shows only the agent's changes rather
  than the upstream commits the rebase picked up. Worktrees created before
  this change, and ones whose base branch was deleted, keep comparing against
  `baseCommit`. Not `[semantic]`: the response shape and what it
  means (the agent's changes) are unchanged, so no `protocolVersion` bump. (2026-10-13, [79046d0](https://github.com/arafatamim/ferngeist-acp-gateway/commit/79046d0))

- `v1.0.0` — connecting starts the agent, and the gateway protocol moves
  `v1` → `v2`:
- `[breaking]` **Connecting starts the agent; `protocolVersion` → `v2`.**
  `POST /v1/agents/{agentId}/start` and `POST /v1/runtimes/{runtimeId}/connect`
  are **removed**. Starting an agent and creating its gateway session are now one
  call: `POST /v1/agents/{agentId}/connect` launches a fresh agent process and
  returns the connect descriptor (`runtimeId`, `protocol`, `scheme`, `host`,
  `websocketUrl`, `websocketPath`, `sessionId`, `attachToken`) — the same shape
  the old connect response returned. Every call launches a new process, so the
  `{"new": true}` body (which only distinguished reuse from a fresh launch) is
  gone. Session and runtime are now 1:1: the session owns its agent process, and
  auto-restart, the stdio pipe lease and the per-runtime exit callback are
  removed. Reconnect is unchanged: `POST /v1/sessions/{id}/resume` then
  `GET /v1/acp/{runtimeId}?sessionId=&attachToken=`. (2026-10-11, [b87da6a](https://github.com/arafatamim/ferngeist-acp-gateway/commit/b87da6a))
- `[semantic]` `POST /v1/agents/{agentId}/stop` — still stops every runtime for
  the agent, now by closing each gateway session that owns one. Behaves the same
  from a client's point of view; returns `503` when the session service is
  unavailable. (2026-10-11, [b87da6a](https://github.com/arafatamim/ferngeist-acp-gateway/commit/b87da6a))
- `[semantic]` `POST /v1/runtimes/{runtimeId}/restart` — launches a fresh agent
  and session first and only then closes the session owning the runtime, so a
  failed launch leaves the old session running. Its response now carries
  `sessionId` and `attachToken` (additive fields) alongside the new `runtimeId`.
  Only the device that owns the runtime's session may restart it; another
  device gets `403`. The `env` override body and its
  `gateway.runtime.restart_env` scope are unchanged. (2026-10-11, [b87da6a](https://github.com/arafatamim/ferngeist-acp-gateway/commit/b87da6a))
- `[additive]` `POST /v1/agents/{agentId}/connect` and
  `POST /v1/runtimes/{runtimeId}/restart` return `502` with the agent's exit
  error when the agent exits during startup, instead of a generic `500`.
  (2026-10-11, [85b27ab](https://github.com/arafatamim/ferngeist-acp-gateway/commit/85b27ab))
- `[semantic]` Agent objects from `GET /v1/agents` no longer carry
  `launch.restart`: the gateway never restarts an agent, so the policy had no
  effect. (2026-10-11, [85b27ab](https://github.com/arafatamim/ferngeist-acp-gateway/commit/85b27ab))
- `[semantic]` `GET /v1/status` `runtimeCounts` and the diagnostics runtime
  summary — the `stopping` and `circuitOpen` counters are removed (stopping is
  no longer a distinct runtime state, and the restart circuit breaker is gone).
  `GET /v1/runtimes` runtime objects likewise drop `restartAttempts`,
  `failureStreak` and `circuitOpen`. (2026-10-11, [b87da6a](https://github.com/arafatamim/ferngeist-acp-gateway/commit/b87da6a))
- `[semantic]` Not client-visible: the database drops the unused
  `gateway_sessions.leaseholder` column on first start. Gateway `v0.13.0` and
  earlier cannot use the migrated database, so downgrading the gateway is not
  supported. (2026-10-11, [85b27ab](https://github.com/arafatamim/ferngeist-acp-gateway/commit/85b27ab))
- `v0.13.0` — gateway-managed worktrees and session-scoped workspace
  endpoints. Protocol version remains `v1`.
- `[additive]` `POST /v1/worktrees`, `GET /v1/worktrees`,
  `DELETE /v1/worktrees/{worktreeId}` — paired clients holding `control` scope
  can create a git worktree (a new branch checked out at
  `<repo>/.worktrees/<branch>` for parallel agents), list managed worktrees
  with `ahead`/`dirty` state, and remove them. (2026-10-11, [3631ac6](https://github.com/arafatamim/ferngeist-acp-gateway/commit/3631ac6))
- `[additive]` Workspace endpoints (`/files`, `/git/status`, `/git/diff`)
  accept an `acpSessionId` query parameter to read one chat's project
  directory when the agent hosts several; without it they use the most
  recently opened session's directory. An unknown id returns `404`.
  (2026-10-11, [22c2073](https://github.com/arafatamim/ferngeist-acp-gateway/commit/22c2073))
- `v0.12.0` — push notifications move from FCM HTTP v1
  to Web Push, encrypted end to end and signed with a VAPID key the gateway
  generates on first boot (`GET /v1/devices/push-config` hands the public key
  out); `FERNGEIST_GATEWAY_FCM_CREDENTIALS_FILE` is gone. ACP
  `elicitation/create` (unstable) is forwarded to clients and pushed as
  `permission_request`, and a session whose agent awaits an unanswered request
  survives up to 24 h. Session and stream reliability: no dropped frames on a
  `session/load` burst, replays that carry the user's own turns, no false crash
  pushes or duplicate notifications, and clean cross-platform install, update,
  and package-upgrade behavior. Protocol version remains `v1`: every change is
  additive or preserves existing client behavior.
- `[additive]` ACP `elicitation/create` (unstable) — forwarded to the client
  like any agent request and pushed as `permission_request` ("Input
  Required"). A request-scoped elicitation's `params.requestId` is rewritten to
  the id the client used, since the agent only sees the gateway's translated
  id; unanswered session-scoped ones are re-sent after `session/load`. A
  disconnected session whose agent awaits an unanswered request now survives
  up to 24 h instead of `MaxDisconnected`. (2026-10-07, [7bdc7f5](https://github.com/arafatamim/ferngeist-acp-gateway/commit/7bdc7f5))
- `[additive]` Web Push delivery — `GET /v1/devices/push-config` returns the
  gateway's `vapidPublicKey`, and `POST /v1/devices/push-token` accepts
  `{"platform":"webpush","subscription":{endpoint, keys:{p256dh, auth}}}`.
  Pushes are now Web Push messages, encrypted end to end, whose decrypted body
  is a JSON object with the former FCM `data` keys; the client posts the
  notification itself. FCM HTTP v1 delivery, its `notification` block and
  `FERNGEIST_GATEWAY_FCM_CREDENTIALS_FILE` are removed: a legacy
  `platform: "android"` token is still accepted but no longer delivered to. No
  `protocolVersion` bump — push is best-effort, and a client that has not
  moved to Web Push keeps working without pushes. `progress` pushes now fire
  only while a prompt runs, a cancelled turn no longer pushes `turn_complete`,
  and an empty-success turn pushes one `agent_error` instead of two.
  (2026-10-07, [7b01417](https://github.com/arafatamim/ferngeist-acp-gateway/commit/7b01417))
- `[semantic]` The update-available push uses a new `category`,
  `gateway_update`, instead of `progress`, so it is no longer collapsed or
  expired like live progress. No `protocolVersion` bump: an unknown category
  falls back to the client's default channel. (2026-10-07, [071a23a](https://github.com/arafatamim/ferngeist-acp-gateway/commit/071a23a))
- `v0.11.3` — reconnect and long-transcript stability:
  a reattached client's `session/load` replay now carries the user's own turns,
  a prompt issued on an earlier connection ends with the new
  `_ferngeist/turn_ended` notification rather than an unmatchable reply, and a
  client whose outbound backlog overflows (128 MiB) is disconnected instead of
  being sent a stream with holes in it. A long replay is also no longer killed
  by the WebSocket keepalive. Protocol version remains `v1`: every change is
  additive or preserves existing client behavior.
- `[additive]` `_ferngeist/turn_ended` — a new gateway→client notification on
  the ACP WebSocket, sent when a `session/prompt` issued on an **earlier**
  connection finishes while a new connection is attached:
  `{"jsonrpc":"2.0","method":"_ferngeist/turn_ended","params":{"sessionId":…,"stopReason":…}}`.
  Client request ids are now translated to gateway-unique ids on the way to the
  agent and restored on the way back, so a reply reaches the connection that
  asked for it. A prompt from an earlier connection therefore cannot be
  answered with a JSON-RPC result — the id it would carry was never issued on
  the current connection — and its turn ends with this notification instead;
  replies to any other earlier-connection request are withheld. A client that
  ignores unknown methods simply never sees a reply for that prompt — the frame
  it used to receive carried the old connection's id, which it could not match
  to a request anyway — while a client that handles the notification can clear
  that turn's streaming state. Underscore-prefixed per ACP's extension rule.
  (2026-10-05, [35031e1](https://github.com/arafatamim/ferngeist-acp-gateway/commit/35031e1))
- `[additive]` `session/load` replay on reconnect — the replay now carries
  `user_message_chunk` updates for the user's prompts, not only the agent's
  replies, so a reattached client no longer folds every reply since the gateway
  took over the session into one message with no user turn between them. The
  per-session buffer is bounded (8 MiB) and trims from the oldest end to a turn
  boundary, so a replay never opens partway through a reply. Clients that
  render `user_message_chunk` see the missing user turns restored; clients that
  ignore it are unaffected. (2026-10-05, [35031e1](https://github.com/arafatamim/ferngeist-acp-gateway/commit/35031e1))
- Backlog overflow disconnects instead of corrupting the stream — the per-client
  outbound queue was a 64-frame channel that silently discarded the overflow,
  so a `session/load` burst (one frame per streamed chunk — thousands of frames
  in milliseconds against a client draining one WebSocket write at a time)
  reached the client with holes in it: turns glued together, or the
  `session/load` response itself missing. The queue is now unbounded in frames
  and capped at 128 MiB of queued bytes; a client past the cap is disconnected
  and logged (`client backlog exceeds cap`) rather than sent a corrupt stream.
  A long replay is also no longer killed at its first keepalive ping: the
  keepalive's 10 s pong wait no longer closes a connection whose writes are
  still completing. No `protocolVersion` bump and no client change required —
  the JSON shapes are unchanged, and a client that reconnects and re-issues
